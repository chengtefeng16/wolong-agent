## 宪法级补充：长期协作规则（必须写入底座备忘）

### 一、协作方式铁律
后续协作中，必须持续遵守以下规则：

1. 把当前项目使用者当小白，不默认其熟悉代码定位与模块关系。
2. 尽量采用“整页删除 + 整页粘贴”式修改，不让用户做零碎定位、局部替换和高出错率操作。
3. 每一步尽量给出：
   - 当前在哪个文件
   - 整页替换还是局部操作
   - 替换后如何核实
4. 每次关键替换后，优先执行最小核实流程：
   - py_compile
   - import smoke test
   - 主流程运行验证
5. 不允许只给大方向而不给落地操作。
6. 必须持续手把手、一步一步指导，降低出错率。

### 二、主干推进纪律
1. 必须持续回看完整公共主干，不得遗漏模块。
2. 分支能力长成后，必须及时回归主干，沉淀共性。
3. 所有新增能力都要先判断：
   - 这是公共底座能力？
   - 还是某个垂直 Agent 的专属逻辑？
4. 若一次做不完，可分刀、分期、分阶段推进。
5. 但凡确认重要的能力，不得遗忘，必须写入检查点 / 宪法 / 路线备忘。

### 三、关键节点纪律
1. 关键节点必须写入 PROJECT_CHECKPOINT / 宪法 / 备忘。
2. 关键节点必须提醒并尽量产出灾难备份。
3. 灾难备份默认优先追求：
   - 详细
   - 完整
   - 可恢复
4. 长对话、换对话、换阶段后，也必须延续这些规则，不得遗忘。

## 宪法级补充：AgentOS 底座“学习基因 / 取经基因”

### 一、底座必须具备主动学习能力
AgentOS / 千秋基座不应只是“会执行的系统”，还必须逐步成长为“会学习、会复盘、会自我修正的系统”。

底座后续必须内生以下基因：

1. 主动学习
2. 主动复盘
3. 好的保持
4. 不好的改正
5. 从多 Agent 实践中总结共性规律
6. 让底座自己越来越聪明，而不是只会重复过去的动作

### 二、从人与系统协作中学习
底座不仅要处理业务任务，也要从“人和系统如何协作”中学习。

必须逐步总结：
- 哪种协作方式更顺
- 哪种交互方式更省错
- 哪种指令方式更利于落地
- 哪种阶段最容易偏航
- 哪些地方最容易让用户卡住
- 哪些环节必须改成更低出错率的流程

原则：
- 协作做得好的，保留并固化
- 协作做得不好的，分析原因并改正

### 三、从底座自身建设中学习
在 AgentOS 建设过程中，底座自己也要不断复盘：

- 哪些设计做得好
- 为什么做得好
- 哪些设计做得不好
- 为什么做得不好
- 哪些模块边界清晰
- 哪些模块职责冲突
- 哪些地方应回主干再收口
- 哪些地方只是长了枝条但未沉淀成主干能力

原则：
- 做得好的，固化
- 做得不好的，纠正
- 不允许只往前堆模块，不做回看与复盘

### 四、从各个垂直 Agent 的实践中学习
后续卧龙、佛学、中医、法律、范蠡、凤雏等各个垂直 Agent 的实践，都不应只是“个体表现”，而应成为底座学习的样本。

底座必须学会总结：
- 哪个 Agent 做得好
- 为什么做得好
- 哪个 Agent 做得不好
- 为什么做得不好
- 哪些成功经验可抽为公共能力
- 哪些失败经验可转为边界规则、预警规则、自愈规则、测试规则

原则：
- 好的保持
- 不好的改正
- 从一个个 Agent 的实践中“取经”
- 让底座越来越聪明、越来越稳、越来越强

### 五、学习基因的长期目标
AgentOS / 千秋基座长期不能只是一套“静态规则系统”，而应逐步成长为：

- 会总结的底座
- 会复盘的底座
- 会吸收经验的底座
- 会修正自己的底座
- 会从多个 Agent 中抽共性的底座
- 会越做越聪明的底座

这应被视为底座长期基因，而不是一次性功能。

## 宪法级补记：本次检查点协作错误反思与基因修正

### 一、本次错误是什么
本次出现的错误是：

在处理 `PROJECT_CHECKPOINT.md` 这种“宪法级 / 历史沉淀级 / 主干总表级”文件时，错误地给出了偏总结性的替换稿，并一度让用户面临“用较短新稿覆盖较长旧稿”的风险。

问题本质不是内容写错，而是：

- 没有先充分区分“增量追加”与“全文替换”
- 没有先充分确认旧文件已经承载大量历史沉淀
- 没有把 `PROJECT_CHECKPOINT.md` 视为“长期主档案”而不是普通阶段记录
- 在高价值长文件面前，错误使用了不够稳妥的协作策略

### 二、为什么会犯这个错误
原因总结：

1. 把“阶段总结稿”误当成“完整覆盖稿”
2. 没有先默认保护旧文件历史沉淀
3. 没有优先采用最低风险策略
4. 没有在输出替换稿前，先强调这是“摘要增量稿”还是“完整合并稿”
5. 没有把“宪法级文件”的协作权重拉到最高

### 三、从这次错误中学到什么
这次必须明确学到：

1. 宪法级文件 ≠ 普通文件
2. 长期检查点文件 ≠ 临时阶段记录
3. 对高价值长文档，默认优先：
   - 追加
   - 局部替换
   - 合并后再整页替换
4. 不能因为当前新内容是对的，就忽略旧内容同样重要
5. “保护历史沉淀”本身就是主干纪律的一部分

### 四、后续强制执行的新规则
从本次开始，针对 `PROJECT_CHECKPOINT.md` / 宪法 / 主干总表 / 长期备忘 文件，必须强制执行以下规则：

#### 规则 1：默认优先追加，不默认整页覆盖
若只是新增阶段成果，默认输出：
- “追加到文件末尾的新章节”
而不是整页替换稿。

#### 规则 2：只有完整合并过旧全文，才允许给整页替换版
若未完整回看旧文件并完成合并重构，不得轻易输出“完整替换全文稿”。

#### 规则 3：必须先判断文件类型
每次改文件前，先判断：
- 普通阶段文件
- 主干文件
- 宪法文件
- 长期档案文件
- 历史沉淀文件

文件级别越高，越要保守修改。

#### 规则 4：先保留旧资产，再新增新资产
对于高价值文件，协作时默认原则应为：
- 先保护旧内容
- 再增加新内容
- 最后才考虑重构整合

#### 规则 5：阶段总结稿不得冒充完整历史合并稿
后续输出时必须明确标注：
- 这是追加稿
- 这是局部替换稿
- 这是完整合并后的整页替换稿

不允许混淆。

系统不仅要学会“写新内容”，还必须学会“尊重旧内容的历史价值”。

#### 新增学习基因 4
协作优化不只是代码优化，也包括：

- 用户出错率控制

#### 新增学习基因 5

## [CHECKPOINT] 从外部建议取精去糟后，固化进 AgentOS 宪法/协作OS 的治理条文（卧龙主线阶段版）

适用阶段：
- AgentOS / 卧龙主线底座对接中
- 执行层治理链逐步打通阶段
- 低风险样例验证阶段
- 局部放权、小范围自动执行测试前后阶段

### 一、放权与治理总原则

1. 坚持最小权限原则  
   任何自动执行能力默认从最小权限开始，不得一开始放开全权限。

2. 坚持白名单优先原则  
   任务类型、动作、渠道、时段、客户范围、风险等级、业务阶段等，均应优先采用白名单机制，而不是黑名单兜底。

3. 坚持分级放权原则  
   自动化能力必须按层级逐步放开，至少包括：
   - L0_disabled
   - L1_generate_only
   - L2_assisted_send
   - L3_limited_auto_send
   - L4_full_auto_send

4. 坚持人类最终确认权  
   高风险业务、关键承诺、重要金额、重要条款、出口政策与合规判断等，必须保留人类最终确认权。

5. 坚持渐进式放权  
   放权必须从小范围、小时段、小权限开始，确认稳定后，再逐步扩大到更长时段、更高权限、更大范围，不得一次性全面放开。

---

### 二、执行层双闸门原则

1. AgentOS 执行层必须长期保持“双闸门”机制：
   - 人工复核闸门
   - delegation 放权策略闸门

2. 任一闸门未通过时，执行层必须硬拦截真实外发，不得只在结果层提示而执行层放行。

3. 执行层的真实发送、桌面输入、接口调用、外部页面提交等动作，必须受治理闸门统一约束。

4. 所有“可生成但不可真实发送”的场景，必须明确区分：
   - 可生成草稿
   - 不可真实外发
   - 可进入人工审核
   - 不可绕过执行层硬拦截

---

### 三、delegation 放权治理优先级原则

1. delegation 内部原因判断必须遵守清晰的治理优先级，不可混乱返回。

2. 当前阶段已固定的优先级应至少包括：

   - manual_review_required
   - outbound_not_ready
   - delegation_master_switch_off
   - delegation_disabled
   - permission_level_not_allowed_for_customer_send
   - time_window_not_allowed
   - action_not_allowed / l1_candidate_but_send_not_enabled
   - channel_not_allowed
   - risk_level_not_allowed
   - business_stage_not_allowed

3. 原因返回必须尽量反映“最上层拦截原因”，不得把更下游的小原因覆盖更上游的大原因。

4. 当前已验证通过的治理收敛原则包括：
   - 总开关优先于下游限制
   - 权限层级优先于动作白名单
   - delegation 拦截需正确置位 `send_blocked_by_delegation = True`

---

### 四、时段放权与连续执行原则

1. 自动执行不得默认 24 小时全时段放开，必须支持按时段配置。

2. 时段放权必须可配置、可逐步扩展，例如：
   - 2 小时
   - 4 小时
   - 8 小时
   - 16 小时
   - 24 小时

3. 时段放权应支持：
   - 单时段
   - 多时段
   - 白天/夜间分别配置
   - 不同业务时段差异化配置

4. 后续若推进 24 小时连续执行，必须以前面多个阶段的稳定验证为前提，不得跳步。

---

### 五、数据安全与记忆隔离原则

1. 高敏数据默认应优先采用本地化、私有化、分级化处理，不得无边界暴露给外部模型或外部系统。

2. 敏感字段应具备脱敏机制，至少包括：
   - 电话
   - 地址
   - 证件号
   - 金额
   - 合同关键号
   - 客户隐私标识

3. 记忆库必须具备隔离原则：
   - 不同客户数据不串
   - 不同业务数据不混
   - 不同 agent 的长期记忆不得随意污染彼此

4. 记忆必须具备有效期与清理机制，过期记忆不能无限堆积。

---

### 六、日志、审计、回滚原则

1. 所有关键任务必须具备唯一任务 ID、执行 ID、日志链路与决策追踪能力。

2. 关键动作必须留痕，至少包括：
   - 谁触发
   - 为什么执行
   - 调用了什么工具
   - 返回了什么结果
   - 为什么被放行或拦截

3. 高风险操作必须支持：
   - 审计
   - 暂停
   - 回收
   - 回滚

4. 关键节点必须持续强化全链路日志，而不是只保留最终结果。

5. 不要求暴露模型全部内部思维，但必须保证：
   - 关键决策依据可追溯
   - 关键执行链可追溯
   - 关键风险原因可追溯

---

### 七、稳定性、防熔毁、防失控原则

1. 失败自动重试必须有限次数，不得无限重试。

2. 连续失败必须支持熔断，防止执行层死循环。

3. 必须逐步完善：
   - API 不可用降级
   - 死循环检测
   - 超时保护
   - 上下文溢出保护
   - 长对话切割/摘要
   - 无效请求自动拦截

4. 上下文过长、日志过大、回放数据过大、重复失败步堆积等，都必须进入系统性治理范围，而不是临时补丁处理。

---

### 八、幻觉防范与业务准确性原则

1. 金额、报价、条款、政策、编号、时间、合规判断等关键信息，必须二次确认。

2. 不得让 AI 编造未授权、未校验、无依据的业务内容。

3. 业务判断中应坚持：
   - 知识库 / 规则 / 白名单优先
   - 模型推理其次
   - 不确定则转人工

4. 任何影响客户决策、公司责任、法律合规和财务承诺的内容，默认不得由 AI 单独最终拍板。

---

### 九、人机协同闭环原则

1. 高风险业务：
   - AI 只能辅助
   - 必须人工决策

2. 中风险业务：
   - AI 草拟
   - 人工审核
   - 执行层受控放行

3. 低风险业务：
   - 可在放权规则内逐步自动执行
   - 但仍必须可暂停、可接管、可回收

4. 所有自动化都必须允许人类随时打断、接管与收回权限。

---

### 十、上线节奏与推进纪律

1. 坚持“先低风险、先小范围、先不外发、再只读、再局部操作、最后逐步放开”的上线节奏。

2. 卧龙主线推进中，必须坚持：
   - 先把治理链打实
   - 再扩大自动执行
   - 再讨论大规模商业化放量

3. 商业变现、平台化、生态化等中长期路径可以保留为远期参考，但不得干扰当前主线。

4. 当前阶段优先级必须始终服从：
   - 主链治理闭环
   - 执行层硬拦截
   - 放权策略可解释
   - 小样例可验证
   - 关键节点可备份可恢复

---

### 十一、当前已沉淀的阶段性成果（供后续接力时回看）

1. 卧龙执行层已形成“双闸门”第一版闭环：
   - 人工复核闸门
   - delegation 放权策略闸门

2. delegation 已完成的阶段性验证包括：
   - 总开关优先
   - 权限层级优先于动作白名单
   - delegation 原因可解释
   - delegation 拦截标志可正确置位
   - 低风险、无人工复核样例可专门验证 delegation 分支

3. 当前主线方法论继续固定为：
   - 稳扎稳打
   - 步步为营
   - 先主干，后枝叶
